## 4. Open decisions — recommended, not yet confirmed

These are implementation-detail forks that came up while designing around §3's answers. Each has a
recommendation; flag any that should go the other way before Phase 1/3 starts.

**4.1 — Where does the Phase 3 Zoho push actually trigger from?**
**Recommended:** piggyback on the quote's *existing* status transition. When a coordinator moves a
quote's `status` from `draft` → `sent` (a control that already exists in `ProposalEditorClient`),
that's also the moment we push to Zoho and move the linked Deal to **"Proposal Sent"** — the two
status changes are conceptually the same event, so one action drives both. Alternative: a separate
"Push to Zoho" button, decoupled from the internal status field.

**4.2 — Exact OAuth scope for the PDF attachment.**
Confirmed **not** covered by the current read-only scope (`POST .../Deals/1/Attachments` → `401
OAUTH_SCOPE_MISMATCH`, tested live). The exact scope string needed (likely something under
`ZohoCRM.modules.deals.{CREATE|UPDATE}`, but Zoho's attachment permissions aren't fully confirmed from
here) **must be verified against Zoho's own API docs at implementation time** — this plan deliberately
does not guess a scope name with false confidence.

**4.3 — Which CRM context to surface, and where (§3.7).**
Verified readable with zero new scope: an Account's related **Deals**, **Notes**, and **Activities
(Tasks/Calls/Events)**. **Recommended:** show related **Deals** only, inline in the existing
`ZohoAccountLookup` picker ("this company has bought from us before — 1 prior deal, Closed Won,
$X") — the single most decision-relevant fact for someone about to quote them. Notes/Activities are
noisier and better left for a later pass if actually wanted.

**4.4 — Preview → Confirm: recompute on confirm, or persist exactly what was shown?**
**Recommended: persist exactly what was previewed.** The engine is a pure function
(`planSeeds()`/`planSchedule()` already return a plan without writing anything — this is why adding a
preview step is cheaper than it sounds, see §7.2), so the "Confirm" action should write the *same*
plan object the coordinator reviewed, not silently recompute against whatever the roster/capacity
data looks like a few seconds later (avoids a subtle bait-and-switch if someone edits a teammate's
weekly hours mid-review).

**4.5 — Does the preview step also apply to "Sync schedule" (existing projects), or only the first
"Start project"?**
**Recommended: both**, for consistency — `regenerateSchedule` already calls the exact same
`planSeeds()` helper, so the preview UI can be shared rather than built twice.

## 5. Verified: current Zoho access, and what Phase 1 needs

| Check | Result |
| --- | --- |
| Current granted scopes | `ZohoCRM.modules.READ`, `users.READ`, `org.READ`, `settings.READ` (read-only, frozen at consent) |
| `GET Accounts/{id}/Deals` | **200** — works today, no new scope |
| `GET Accounts/{id}/Notes` | **200** — works today, no new scope |
| `GET Accounts/{id}/Tasks` (activities) | **200** — works today, no new scope |
| `PUT Deals/{id}` (field/stage update) | **401** `OAUTH_SCOPE_MISMATCH` — needs Phase 3 scope |
| `POST Deals/{id}/Attachments` | **401** `OAUTH_SCOPE_MISMATCH` — needs Phase 3 scope |

**Phase 1 needs zero Zoho-side changes.** Phase 3 needs new scope(s) added to `ZOHO_SCOPES`, a
redeploy, and — because an existing refresh token can never gain new scope — a **Disconnect →
Connect** re-consent by someone whose Zoho account can edit Deals (this is a real dependency: it must
be done by a person with CRM edit rights, not necessarily the same person who did the original
read-only connect).

## 6. The real risk shift at Phase 3

Every Zoho feature shipped before this plan is read-only: a bug can fail to *show* something, never
corrupt anything. Phase 3 changes that. Once write scope exists, a bug in this app can **actually
modify a live Deal in a CRM with ~926 real deals** — wrong stage, wrong amount, a duplicate
attachment. That's a materially different risk tier, so Phase 3 should get:

- **Idempotency** — clicking "send" twice (double-click, retry after a network blip) must not attach
  the PDF twice or re-fire the stage move if it already happened. Track a `pushed_at` timestamp inside
  the existing `proposals.zoho` jsonb (no new column/migration — just a new key) and guard on it.
- **A dedicated security pass before shipping** — mirroring the audit already run on the read-only
  Zoho work this session (route gates, `server-only`, no secrets in the client bundle, RLS canary
  tests) — this time specifically checking the write path can't be triggered by the wrong role or
  replayed.
- **A visible failure state.** If the Zoho write fails, the quote's own `status` should still have
  changed (don't roll back the thing the user asked for) — but the CRM-out-of-sync state must be
  surfaced, not swallowed, so someone knows to retry or push manually.

## 7. Work breakdown by phase

### Phase 1 — Richer CRM context (read-only, no scope change) — ✅ SHIPPED 2026-08-01
- **Backend:** `/api/zoho/accounts` now enriches every company in the result set with its prior
  Deals via **one batched** `Deals/search?criteria=((Account_Name:in:<all ids>))` call. Verified live:
  25 ids resolve in a single ~540ms request — a per-account related-list lookup would have been 25
  calls per search. Enrichment is best-effort (`dealsByAccount()` swallows failures and returns `{}`),
  so a deals-lookup problem can never break the company list.
- **Frontend:** `ZohoAccountLookup` shows a "N prior deals — <name> (<stage>)" line under each
  company. Companies with no deals render nothing (no "0 deals" noise).
- **Decision applied:** §4.3 — Deals only; Notes/Activities skipped as noisier.
- **Cost:** search latency goes from ~0.8s to ~1.4s (the batched call is necessarily sequential — it
  needs the account ids first). Acceptable behind the existing 400ms debounce + spinner.
- **Risk:** none realised — purely additive, read-only, no re-consent. Lint stayed at baseline.

### Phase 2 — Preview → Confirm for the generated schedule
- **Backend:** split the "compute" and "write" halves that are currently fused inside
  `convertToProject` / `regenerateSchedule`. The pure half (`planSeeds()` → assignee + dates per line
  item, phase sprint dates, finish date) already exists and needs no changes — it's the "write sprints
  + tasks + assignees to Supabase" half that needs to move behind a new explicit "confirm" call,
  taking the previously-computed plan as its input (per §4.4, not recomputing).
- **Frontend:** the "Start project" dialog (and the "Sync schedule" dropdown per §4.5) gets a second
  step: render the computed plan (assignee + dates per task, sprint date ranges, unassigned/flagged
  items) before the existing "Create project" button — which becomes "Confirm & create" and now writes
  the previewed plan rather than computing fresh.
- **Risk:** low — no Zoho involvement; the underlying engine is unchanged and already
  self-check-tested (`lib/assignment/plan.check.ts`).

### Phase 3 — Zoho write-back (the real new capability)
- **Prerequisite:** widen `ZOHO_SCOPES`, redeploy, Disconnect → Connect re-consent by someone with CRM
  edit rights (§5). Confirm the exact attachment scope against Zoho's docs (§4.2) before writing code.
- **Backend:** a new `/api/zoho/deals/[id]/push` (or similar) route, gated the same way every other
  Zoho route is (`requireZohoReader` → probably needs a stricter `requireZohoWriter`, admin+manager
  still, since this now mutates production CRM data). Writes `Amount`, `Quote_number`, `Stage`, and
  uploads the PDF via the Attachments endpoint. Idempotent per §6.
- **Frontend:** wire the push into the existing status control (§4.1) — when a coordinator marks a
  quote "sent" and it has a linked Zoho Deal (`quote.zoho.deal_id` already exists from the import
  flow), fire the push; surface success/failure inline (not just a toast that can be missed).
- **Risk:** the only phase with real production risk — see §6. Ship last, test hardest.

## 8. Sequencing

| Phase | Depends on | New Zoho scope? | Size | Risk |
| --- | --- | --- | --- | --- |
| 1 — CRM context | — | No | S | None |
| 2 — Preview/Confirm | — (parallel to 1) | No | M | Low |
| 3 — Write-back | Re-consent by a CRM-edit-capable person | **Yes** | M–L | The one that matters |

Phases 1 and 2 don't depend on each other or on Phase 3 — they can ship in either order, or in
parallel, whenever picked up. Phase 3 is deliberately last: it's the only phase blocked on someone
outside this codebase (Zoho re-consent) and the only one that can touch production CRM data.
